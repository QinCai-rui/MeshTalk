Architecture

MeshTalk is a peer‑to‑peer encrypted messaging system. The Python backend owns identity, networking, encryption, persistence, and transport selection. It runs as a daemon and communicates with local clients (OpenTUI or CLI) over a Unix‑domain socket.

The backend consists of several cooperating modules:

  • Identity – Ed25519 signing key and X25519 encryption key, stored in ~/.meshtalk/identity.json.
  • Discovery – UDP broadcast on port 24890 for LAN peers.
  • PeerManager – manages connections (LAN TCP, remote UDP, DERP relay) and handshakes.
  • MessageRouter – routes E2EE messages between peers, friend‑only inbound.
  • GroupRouter – fan‑out group messages to active roster members, with offline queueing.
  • FileTransferManager – chunked encrypted file transfers (≤50 MiB).
  • RendezvousService – connects to the control server for remote discovery and room membership.
  • IPCServer – exposes JSON‑RPC over the local socket; CLI/TUI are clients.

All chat traffic and file chunks are end‑to‑end encrypted with ephemeral X25519 and AES‑256‑GCM. The control server never sees plaintext.

Connectivity

MeshTalk provides three transport paths, prioritised in this order:

  1. LAN TCP – automatic discovery via UDP broadcast (port 24890); deterministic TCP connection (port 24891) to the lower peer ID. Works without internet.
  2. Remote UDP – STUN binding request (RFC 5389) via stun.l.google.com:19302 to discover public endpoints. Peers exchange signed endpoint cards through the control service and punch UDP holes directly. Uses the same socket for STUN, punching, and data.
  3. DERP relay – when direct UDP fails, encrypted datagrams are forwarded through the control WebSocket connection. Enabled by default, with per‑peer bandwidth limits (1 MiB/s, 4 MiB burst).

Capabilities are negotiated between peers; if a capability (e.g., file transfer) is missing on either side, that feature is disabled without breaking the connection.

Rooms & Groups

Private rooms are invite‑only. An invite contains an opaque 128‑bit room ID and a 256‑bit room secret, encoded as:

meshtalk:<room_id>.<room_secret>

For named groups, the invite uses the meshtalk-group: prefix and includes an encrypted metadata segment with the group name.

Endpoint cards are signed with Ed25519 and encrypted with AES‑256‑GCM using a key derived from the room secret. The control service stores cards but never sees the secret or plaintext.

Group messages are pairwise fan‑out – each copy is encrypted to a recipient’s X25519 key. Offline members with a known key receive queued messages when they reconnect. Leaves are signed and broadcast.

File Transfer

Files up to 50 MiB can be sent directly between peers. Each chunk (≤28 KiB plaintext) is encrypted with a fresh ephemeral X25519 key (forward secrecy). The receiver reassembles chunks and saves to ~/.meshtalk/files/<file_id>/. Partial transfers can be resumed via missing‑range ACKs. In the TUI, press Ctrl+U to send a file; paste images with Ctrl+V.

Append --help to any command for detailed usage.

Control Server & Relay

The control service (Bun) handles remote room membership and endpoint‑card exchange. It operates over WebSocket (wss:// in production). It stores no messages, only encrypted cards per connection and room.

The embedded DERP relay forwards encrypted datagrams when direct UDP fails. It enforces rate limits (500 frames/s), bandwidth quotas (1 MiB/s, 4 MiB burst), and a limit of 8 concurrent peers per device. Set CONTROL_RELAY_ENABLED=false to disable relay.

bun run dev:control

In the TUI: Ctrl+P → Control server → Use a custom server → ws://127.0.0.1:8787/v1/rendezvous

Limitations

MeshTalk uses X25519 key exchange. It is secure against classical attacks but not quantum‑resistant. For long‑term confidentiality against future quantum adversaries, consider additional protections.
