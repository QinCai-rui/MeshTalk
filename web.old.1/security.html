Security

MeshTalk is built with privacy and encryption at its core. Here's exactly how it works — and its honest limitations.

Post‑quantum warning
MeshTalk uses X25519 (Curve25519) for all key agreement. X25519 is not resistant to quantum computers. An adversary who records encrypted traffic today and later obtains a private key — or builds a fault-tolerant quantum computer — could decrypt past sessions. This is a "store now, decrypt later" risk. Do not use MeshTalk for messages that must remain confidential against nation‑state adversaries with long‑term storage capabilities.

Encryption model

Identity & keys

Each installation has a persistent Ed25519 signing identity and a separate X25519 message-encryption key. The peer ID is SHA‑256 of the Ed25519 public key.

End‑to‑end encryption

Messages use a one‑time ephemeral X25519 key and AES‑256‑GCM. Immutable routing metadata is authenticated by both the encrypted envelope and the sender's Ed25519 signature. Each file chunk uses a fresh ephemeral key for forward secrecy.

Transport security

Direct UDP sessions use signed ephemeral X25519 key exchange. Transport fragments are authenticated; data is encrypted. LAN TCP connections are also authenticated.

Control service & endpoint cards

Room invites contain a random 128‑bit routing ID and an independent 256‑bit room secret. Endpoint cards are signed with Ed25519 and encrypted with AES‑256‑GCM using a key derived from the room secret. The secret never reaches the control server.

What the control service can and cannot see

🟢 Cannot

  • Decrypt endpoint cards or messages
  • Forge signed peer identities
  • Read chat traffic (it never touches the service)
  • Access room secrets
  • Store messages

🟠 Can observe

  • Connection IPs and timing
  • Opaque room IDs and room sizes
  • Relay frame sizes (not content)
  • Rate‑limit activity
  • Whether a peer is online

Threat model & limitations

Invite secrecy

Anyone holding a room invite can join that room. Treat invites as secrets. Send them only through trusted channels. If an invite leaks, create a new room.

Network visibility

Direct peers necessarily learn each other's public IP and UDP port. STUN providers learn the source address of STUN requests. This is inherent to peer‑to‑peer networking.

Group limitations

Groups have no administrators, member revocation, invite rotation, or synchronized history. Each member's roster is local. Missed messages are not replayed.

Relay trust

The DERP relay can observe registration, room IDs, peer IDs, timing, and encrypted frame sizes. It cannot decrypt the frames themselves. Rate limits and quotas bound abuse.

Best practices

  • Treat invites as passwords — keep them secret and share them securely.
  • Create new rooms for each conversation — don't reuse invites.
  • Run your own control server if you don't want to trust the public one.
  • Use --debug only for diagnostics; logs never include private keys or message content.
  • Consider the post‑quantum risk — for highly sensitive data, use a hybrid PQ‑safe solution.
  • Keep your MeshTalk installation updated — run meshtalk update regularly.
Transparency
MeshTalk is open source. You can audit the code, build from source, and verify that it does what we say. The security model is documented in DESIGN.md and PROTOCOL.md.
